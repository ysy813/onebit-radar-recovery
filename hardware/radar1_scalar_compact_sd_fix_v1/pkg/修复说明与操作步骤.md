# SD 启动写入修复：网络成像＋原始数据存储

已定位本次失败原因，并完成独立软件修正版。这里沿用 `radar1_scalar_compact_exp_v1` 的同一份网络 BIT，仅重新编译存储模式 ELF。原工程及旧包保持不变。本版尚需一次实际板测确认。

## 为什么卡有空间仍写入失败

2026-11-03 对用户重新插入的 D: 卡进行只读检查，结果如下：

| 项目 | 读取结果 |
| --- | ---: |
| 文件系统 | FAT32 |
| 每簇字节数 | 32768 |
| Windows 显示可用字节数 | 7939391488 |
| 扫描真实 FAT 得到空闲簇 | 242291 |
| 对应实际空闲字节数 | 7939391488（约 7.39 GiB） |
| FSInfo 缓存记录的空闲簇 | **0** |
| 两份 FAT 分配表 | SHA256 相同 |

FatFs 的当前 BSP 配置为 `FF_FS_NOFSINFO=0`。挂载时，它直接使用 FSInfo 的空闲簇计数。该计数虽为 0，却仍被当成有效数值。分配文件首个数据簇时，`create_chain()` 因而立即返回“无空闲簇”，没有继续查真实 FAT。`f_write()` 在这种情况下返回 `FR_OK=0`，但实际写入字节为 0。这正好复现日志中的 `requested=121 actual=0`；121 字节就是运行清单 CSV 的表头。

因此本次失败发生在 DMA 和网络使能之前。日志中的 `NET enabled=0 done=0 fault=0` 与这个启动顺序一致，不是网络推理失败的证据。空 CSV 可以只占目录项，不能据它被创建成功判断文件内容可写。

目前没有证据确定此前哪个格式化工具或程序写入了错误缓存。两份 FAT 一致也不等于整个文件系统经过完整健康认证。本次未对物理 SD 卡进行写入、删除、格式化或磁盘修复。

## 软件修改

1. 挂载成功后、创建文件及启动采集前，将 RAM 内的 FatFs 空闲计数设为“未知”，再调用原 BSP 的 `f_getfree()`，从 FAT 重新统计真实空闲簇。仅启动时扫描一次，不在实时存储循环扫描。
2. 打印旧缓存、真实空闲簇、可用 MiB 及可存 2 MiB 原始块数。空间确实不足或扫描读取出错时停止，不假装成功。
3. CSV 表头写完后立即 `f_sync()`；确认数据和元数据提交成功后才初始化 DMA、使能网络和存储。
4. 正常文件同步由原 FatFs 负责更新 FSInfo。本版没有直接改写原始扇区的代码，也不靠格式化解决问题。

SD 仍保存原始 RX0 ADC，每完整块 2 MiB，每个 BIN 最多 256 MiB；同名旧文件不覆盖。两电平规则、网络权重、插值、720p60 显示和 DMA 环均沿用原版。全距离网络及实验质量限制不变。

## 文件对应关系

- `pkg/program_onebit_network_storage.tcl`：本次唯一下载入口，执行网络成像＋原始存储。
- `pkg/design_1_wrapper.bit`：原 compact 实验版 BIT 的原样副本，签名 0x71。
- `pkg/onebit_network_storage.elf`：新增启动 FAT 计数扫描及诊断的 PS 程序。
- `software/sd_space.c`：启动空间核验实现；`software/radar_sd_long.c` 为调用入口。
- `bsp/`：复制的匹配 BSP 头文件和库，可独立重编软件。
- `reports/sd_readonly_diagnosis.json`：本次物理卡只读检查结果。
- `reports/fatfs_regression.log`、`reports/STANDARD_CHECK.json`：离线回归及发布检查。

如需查看 PL 网络 IP，继续打开原 `radar1_scalar_compact_exp_v1/project/imaging_storage.xpr`。本目录是独立软件修复包，没有另造一份不同的 Vivado 工程。

## 上板操作

1. 在电脑端安全弹出 SD 卡；FPGA 断电时插回板卡。无需往卡中添加文件，也无需删除原来的空 CSV。停止雷达数据流，连接原来的 JTAG、串口和 HDMI。
2. 提前在 mmWave Studio 保持原 1024 采样点、512 chirp、4RX、500 ms 配置。这次可设置 **60 帧**，约 30 秒后雷达自动停止；不要同时改变采集参数来做本次存储复测。
3. 打开串口日志保存，然后在 PowerShell 执行：

```powershell
Set-Location 'C:\Users\yang\Desktop\SAR_IMAGE\radar1_scalar_compact_sd_fix_v1'
& 'C:\Xilinx\Vitis\2022.1\bin\xsct.bat' '.\pkg\program_onebit_network_storage.tcl'
```

4. 等待串口依次出现以下关键信息。FAT 扫描需要时间，应等待 `ACTION` 再触发；程序发出 ACTION 后约 60 秒内需要收到第一完整块。

```text
Build: radar1-scalar-compact-sd-fix-v1, ...
SD_MOUNT: ... cached_free=0.
SD_SCAN: recounting actual FAT allocation before capture; please wait.
SD_SPACE: counted_free=... free_MiB=... raw_blocks_available=....
SD_FSINFO_STALE: cached=0 actual=...; using scanned count.
SD_SPACE_PASS: FAT allocation verified.
SD_MANIFEST_PASS: 0:/RUNxxxxx.CSV header_bytes=121 synced.
New segment: 0:/LNGxxxxx.BIN, max=256 MiB.
SG DMA armed: ...
BRANCH_ENABLE=3 ...
NETWORK_REQUEST=1 ...
ACTION: ...
```

`SD_FSINFO_STALE` 在计数已被正常同步后可能不再出现，这是正常情况。

5. 出现 `ACTION` 后，按一次 PL_KEY2（超过 50 ms），等 5 秒，再在 Studio 点击 Arm、Trigger Frame。此时 `Stored` 应增加，网络 `enabled=1`、`done` 随推理增加，`fault=0`。
6. 60 帧自动结束后保持板卡供电；连续 5 秒没有新完整块后，程序结束接收并回读 BIN 校验。等待 `Readback PASS` 及最终 `RESULT: PASS, stored=... acquisition_error=0`，再断电取卡。若使用连续帧则先手动 Stop Frame，再按相同方式等待。
7. 完整串口日志保存到本目录 `board_runs/network_storage_sd_fix.txt`，包括启动、SD_SCAN、采集和最后 RESULT。出现任何 FAIL 时保留完整日志，先停止雷达。

网络推理沿用当前实验版，每帧约数秒，显示的整数 FPS 仍可能为 000；这与本次 SD 启动故障是两件事。`image_skip` 记录成像忙时的整帧跳过，不能据此认定原始存储丢块。

## 已验证和待验证

新软件使用 A53 编译器的 `-Wall -Wextra -Werror -O2` 编译通过。使用原 BSP FatFs 源码及内存 FAT32 磁盘的 7 组回归通过：复现旧短写、重新计数后 CSV＋2 MiB 数据写入读回及旧文件保留、正常缓存、错误非零缓存、真实满卡、空间不足、FAT 读错误。同步后的 FSInfo、两份 FAT 和重新挂载也已核对。

发布检查核对 ELF 加载边界、原 AQ/AR 表、库与头文件来源、BIT/PS 初始化脚本一致性及原工程文件 SHA256。最终结果见 `reports/STANDARD_CHECK.json`。

这些验证不代替物理板卡上的实际 SD/DMA/成像联合测试；本次还需上面的单次复测。原网络质量资格仍为实验版，`full_system_timing_signoff=false` 沿用原硬件记录，没有通过软件修复改变该结论。
